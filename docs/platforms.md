# Platforms: desktop, server and Android

OpenShell is not tied to the desktop. The runtime, the agent layer, the control API and the
configuration are the same everywhere; a small **platform adapter** decides how programs are
started and how the app lifecycle is handled. This page describes the platform model, what works
on Android today and where the Android work is going.

## Goals

- **One core, several platforms.** `openshell-core` runs unchanged on Windows, macOS, Linux,
  headless servers and Android. Platform code lives in adapters and hosts, not in the core.
- **The phone as a personal runtime and mini server.** Apps, services, databases, automations
  and agents generated by AI run locally on the phone and stay reachable for your other devices.
- **AI builds, the user does not edit code.** Agents create, extend, test and manage apps through
  the same MCP tools as on the desktop; the platform tells them which building blocks exist there.
- **Connected devices.** Desktop, phone and server are meant to manage and develop projects
  together (see [device mesh](#device-mesh-planned)).

## Layers

```
            ┌───────────────────────── hosts ─────────────────────────┐
            │ desktop app (Tauri)   headless CLI   Android app (planned)│
            │ window, tray, dialogs  terminal       Activity + WebView, │
            │                                       foreground service  │
            └──────────────┬──────────────────────────────┬──────────────┘
                           │ Host trait                    │ lifecycle events
            ┌──────────────▼──────────────────────────────▼──────────────┐
            │ openshell-core: Shell, control API, MCP, remote gateway    │
            │ openshell-agent: policy, approvals, audit, UI bridge       │
            │ openshell-runtime: plan, supervisor, health, logs, static  │
            │                    server, databases, lifecycle            │
            └──────────────┬─────────────────────────────────────────────┘
                           │ RuntimeAdapter
            ┌──────────────▼─────────────────────────────────────────────┐
            │ DesktopAdapter (desktop, server)   AndroidAdapter           │
            │ any program in PATH, job objects   system tools + programs  │
            │ / process groups                   bundled with the app     │
            └────────────────────────────────────────────────────────────┘
```

| Piece | Where | Responsibility |
|---|---|---|
| `Platform` | `crates/config` | `desktop`, `android`, `server` – used in `services[].platforms` |
| `RuntimeAdapter` | `crates/runtime/src/platform.rs` | builds every command (services, setup, build, functions, tasks), reports `Capabilities` |
| `DesktopAdapter` | same | any program from `PATH` or the project; `server` variant without window and tray |
| `AndroidAdapter` | same | only system tools (`/system/bin`) and programs registered by the host (`node` → `libnode.so`) |
| `LifecycleEvent` | `crates/runtime/src/lib.rs` | `foreground`, `background`, `low_memory`, `power_save`, `network` |
| `Host` | `crates/core/src/lib.rs` | window, notifications, approvals – implemented per front-end |
| Remote gateway | `crates/core/src/remote.rs` | the app profile for other devices, protected by a pairing token |

`Runtime::new` / `Shell::launch` pick the adapter for the platform the binary was built for.
Hosts can pass their own with `Runtime::with_adapter` / `Shell::launch_with`.

## Capabilities

Every runtime reports what its platform offers. Agents see it in `app_info` and `GET /v1/status`:

```json
"platform": {
  "platform": "android", "os": "android", "arch": "aarch64",
  "processes": "restricted", "background": "foreground_service",
  "file_watching": true, "app_window": true, "tray": false, "installers": false
}
```

| Field | Desktop | Server | Android |
|---|---|---|---|
| `processes` | `full` | `full` | `restricted` – system tools and bundled programs |
| `background` | `always` | `always` | `foreground_service` – needs a foreground service to stay alive |
| `app_window` / `tray` | yes / yes | no / no | yes / no |
| `installers` | yes | no | no |

## Configuration

```json
{
  "services": [
    { "name": "compiler", "command": "cargo run", "platforms": ["desktop", "server"] },
    { "name": "sync", "command": ["node", "sync.mjs"], "background": "pause" }
  ],
  "runtime": { "remote": { "enabled": true, "bind": "0.0.0.0", "port": 7420 } }
}
```

- `services[].platforms` – only run on these platforms. Like `modes`, services for other platforms
  are left out of the plan and dependencies on them are dropped.
- `services[].background` – `keep` (default) or `pause`: stop while the app is in the background,
  start again when it returns. Only matters on platforms with `background: foreground_service`.
- `runtime.remote` – the [remote gateway](#remote-access).

## Android

### What runs on Android

Android allows an app to execute only files inside its APK (the native library directory) and
system tools – files written at runtime cannot be executed (W^X, Android 10+). There is no `PATH`
with toolchains. The `AndroidAdapter` follows these rules and turns violations into a clear error
that tells the developer or the agent what to use instead:

```
`cargo` cannot run on Android: apps may only start system tools and programs shipped with the
app (bundled: node). Use a static frontend, the built-in database or functions for a bundled
interpreter, or limit this service with "platforms": ["desktop", "server"]
```

| Building block | On Android |
|---|---|
| Static frontend (`frontend.dist`) | ✅ built-in static server |
| Built-in database (SQLite, migrations, SDK, agents) | ✅ compiled into OpenShell |
| Functions (`capabilities[].run`) | ✅ with system tools (`sh`) or a bundled interpreter |
| Services | ✅ with a bundled program (`node`, `python`, own binaries in the APK) |
| HTTP capabilities, OpenAPI import, UI bridge, MCP | ✅ unchanged |
| Dev-server frontends, build steps with toolchains | ❌ – build on the desktop, or limit with `platforms` |

The host registers what it bundles:

```rust
let adapter = AndroidAdapter::new()                        // allows /system/bin
    .with_executable_dir(native_library_dir)               // every executable in the APK
    .with_program("node", native_library_dir.join("libnode.so"))
    .with_program("python", native_library_dir.join("libpython.so"));
let shell = Shell::launch_with(project, Mode::Production, host, Arc::new(adapter)).await?;
```

Without a host (for example in a terminal app) the adapter reads `OPENSHELL_ANDROID_EXEC_DIRS`
(`:`-separated) and `OPENSHELL_ANDROID_PROGRAMS` (`node=/path/libnode.so;python=/path/libpython.so`);
inside Termux its `$PREFIX/bin` is allowed automatically.

### Lifecycle, battery and network

Android stops apps in the background. The host forwards the Activity and system events:

| Android | `LifecycleEvent` | Effect |
|---|---|---|
| `onStart` | `foreground` | paused services start again |
| `onStop` | `background` | services with `"background": "pause"` stop |
| `onTrimMemory(RUNNING_CRITICAL)` | `low_memory` | pausable services stop |
| `PowerManager.isPowerSaveMode` | `power_save` | reported to agents and hosts |
| `ConnectivityManager` callback | `network` | reported (`connected`, `metered`) |

`Runtime::keep_alive()` lists the active services that must keep running (`background: keep`).
While it is not empty the Android host keeps a **foreground service** (type `specialUse` or
`dataSync`, with a persistent notification) alive and asks the user once to exempt the app from
battery optimisation, so the phone can act as an always-on server. When the list becomes empty
the host stops the foreground service and Android may suspend the app.

Hosts send events with `Shell::lifecycle(event)`; for testing on any platform use the CLI or API:

```bash
openshell lifecycle background     # services with "background": "pause" stop
openshell lifecycle foreground     # … and start again
curl -X POST -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"kind":"low_memory"}' $URL/v1/lifecycle
```

### Status

- ✅ The core and the CLI build for `aarch64-linux-android` and `x86_64-linux-android` (CI checks
  the Android build on every push).
- ✅ Verified on an Android 16 emulator: `openshell dev --headless` serves a static frontend,
  migrates the database, runs functions through `/system/bin/sh`, leaves desktop-only services
  out, pauses and resumes services on lifecycle events and serves the app profile to a laptop
  through the remote gateway.
- ✅ Usable today in a terminal app such as Termux (`pkg install nodejs python` adds runtimes).
- ⏳ Android app (see below).

### The Android app (next phase)

The OpenShell Android app is a host around the unchanged core:

1. **Shell app** – Tauri 2 mobile target (same WebView/IPC model as the desktop app) with the core
   as a library; the frontend runs in the app's WebView.
2. **Foreground service plugin** (Kotlin) – keeps the runtime alive while `keep_alive()` is not
   empty, shows a notification with the running services, forwards lifecycle, memory, battery and
   network events, requests the battery-optimisation exemption.
3. **Bundled runtimes** – Node.js and Python as `lib*.so` in the APK, registered with
   `AndroidAdapter::with_program`; optional runtime packs downloaded per app ABI.
4. **App manager** – install, update, start and remove multiple OpenShell apps on the phone; an
   agent creates an app as a project folder, OpenShell runs it, no code editing by the user.
5. **On-device agents** – local models (for example via Ollama-compatible servers on the phone or
   on another device) and remote agents through the gateway.

## Remote access

The remote gateway makes an app usable from other devices – a laptop agent using functions of an
app hosted on the phone, or a phone using an app on a home server.

```json
"runtime": { "remote": { "enabled": true } }
```

```bash
openshell remote     # URL, MCP endpoint, pairing token and a ready MCP client configuration
```

| Route | Auth | Purpose |
|---|---|---|
| `GET /v1/health` | public | app name, platform, version |
| `GET /v1/remote/info` | pairing token | app, platform capabilities, functions |
| `POST /mcp/app` | pairing token | the app profile over MCP (Streamable HTTP) |

Security model:

- Off by default. Only the **app profile** is exposed – the app's own functions, never developer
  tools (files, logs, services, UI automation) and never the admin token.
- A separate pairing token (`.openshell/data/remote-token`, stays the same across restarts). Delete
  the file to revoke all paired devices.
- Requests with an `Origin` header are rejected, so websites in a browser cannot call the gateway.
- Permissions, approvals and the audit log apply as for local agents; remote calls are audited
  with the channel `remote`.
- Plain HTTP: use it in a trusted network or bind it to a VPN address (`"bind": "100.x.y.z"` for
  Tailscale). TLS and per-device tokens are planned.

## Device mesh (planned)

Desktop, phone and server running OpenShell should form one personal mesh:

- **Pairing** – devices exchange per-device tokens (QR code on the phone, `openshell pair` on the
  desktop) instead of one shared token; TLS with pinned certificates.
- **Discovery** – mDNS (`_openshell._tcp`) in the local network, VPN addresses otherwise.
- **Remote control API** – manage services, logs and approvals of another device's apps with the
  same CLI (`openshell --device phone status`).
- **Project sync** – projects as folders synchronised between devices (git-based), so an agent can
  develop on the desktop and deploy to the phone (`openshell deploy --device phone`).
- **Placement** – `services[].platforms` already lets one project describe what runs where; the
  mesh adds "run this service on the server, the UI on the phone".
