Installers (openshell package)

openshell package turns an OpenShell project into a native installer – without writing or compiling any desktop code for your app.

cargo build --release -p openshell-desktop   # once: the generic shell binary
openshell package                            # build + installer for the current platform
openshell package --target msi --out dist    # other formats, copy results to dist/

What happens#

  1. openshell build runs (skip with --skip-build): compiled services (services[].build, e.g. Maven, CMake) and the frontend (frontend.build).
  2. The application files are staged into app/ (see Which files are shipped).
  3. The generic openshell-desktop binary is copied, renamed to your app (my-app.exe) and re-branded with your icon (app.icon, PNG – OpenShell's icon if unset). No compiler is involved.
  4. The Tauri bundler produces the installer(s):
PlatformFormats (--target / package.targets)Default
Windowsnsis (setup.exe, per-user install, no admin rights), msinsis
macOSapp, dmgapp, dmg
Linuxdeb, rpm, appimagedeb, appimage

The bundler downloads its tools (NSIS, WiX, appimagetool) on first use. The staging directory .openshell/package/bin/ is also a portable build: run my-app.exe there without installing.

Installed app behaviour#

%LOCALAPPDATA%\Programs\My App\        (Windows, NSIS per-user install)
  my-app.exe                           the shell, with your icon
  app\openshell.json                   your application
  app\...
  • Starts in production mode (agent permissions from agents.permissions.production).
  • State lives in a per-user directory named after the bundle identifier, e.g. %LOCALAPPDATA%\com.example.myapp\ (Windows), ~/Library/Application Support/com.example.myapp/ (macOS), ~/.local/share/com.example.myapp/ (Linux): logs, audit log, runtime.json and data/, which services get as OPENSHELL_DATA_DIR. Store your database/files there so they survive updates and uninstalls.
  • Single instance: starting the app again focuses the running window. A background instance started for an agent (--mcp) is replaced by the window.
  • my-app.exe --mcp is an MCP server for AI agents on the user's machine (see Agent Interaction Layer).
  • my-app.exe --headless runs the services without a window.

Configuration#

{
  "app": { "name": "My App", "id": "com.example.myapp", "version": "1.2.0", "icon": "assets/icon.png" },
  "package": {
    "publisher": "Example Inc.",
    "homepage": "https://example.com",
    "copyright": "© 2026 Example Inc.",
    "license_file": "LICENSE",
    "targets": ["nsis", "msi"],
    "exclude": ["docs", "**/*.test.js"],
    "include": []
  }
}

app.version must be a semantic version (1.2.0). package.identifier overrides app.id.

Which files are shipped#

By default the whole project except .git, .openshell, node_modules, __pycache__, *.pyc, virtualenvs, .gradle, IDE folders. Add exclude patterns (globs, relative to the project), or list exactly what to ship with include (the config file is always included):

"package": { "include": ["openshell.json", "web", "backend/build/bin"] }   // C++: only the compiled binary
"package": { "exclude": ["backend/src"] }                                 // Java: ship classes, not sources
"package": { "exclude": ["frontend/src", "frontend/public"] }             // ship only frontend/dist

Runtimes#

The installer contains the shell and your app files. Interpreters and runtimes your services need – Python, Node.js, a JRE – must exist on the target machine, or you ship them with the app:

openshell runtime add python 3.12      # declares it in openshell.json and downloads it into runtimes/python
openshell runtime add node 22
openshell runtime add java 21          # Temurin JRE
openshell package                      # the runtime folder is part of the installer

Bundled runtimes come first in PATH for every service, setup and build step, function and task, so `python main.py` uses them without any change. They are built for one system: the release workflow runs openshell runtime install on each build machine before openshell package. See Configuration. Compiled services (C++, Rust, Go, GraalVM native images, self-contained .NET) need nothing extra. Declare the versions a service needs with requires ({ "python": ">=3.10" }); openshell doctor checks them and the app logs a warning at start when they are not met. If a runtime is missing, the loading screen shows the error (java was not found in PATH).

Portable app bundle (.osapp)#

openshell package --target bundle        # dist/my-app-1.2.0.osapp – works on every platform, also in Termux

A bundle is a zip with the shipped files (same include / exclude rules) and openshell-bundle.json (app, identifier, version). It runs unchanged on every OpenShell host:

HostHow
Android appopen or share the .osapp with OpenShell (Android app)
Termux, servers, desktops with the CLIopenshell install my-app-1.2.0.osapp --start

openshell install unpacks into ~/.openshell/apps/<identifier>/ (OPENSHELL_APPS_DIR); installing a newer bundle replaces the files and keeps the app's data (.openshell/). openshell apps lists installed bundles.

One link per system#

A developer builds once, users download one file for their system – without changing the program.

openshell release workflow               # writes .github/workflows/openshell-release.yml
git tag v1.2.0 && git push origin v1.2.0

On every tag the workflow builds in parallel and publishes a GitHub release with:

FileFor
My App_1.2.0_x64-setup.exeWindows (NSIS, per-user install)
My App_1.2.0_aarch64.dmg, My App_1.2.0_x64.dmgmacOS Apple Silicon / Intel
my-app_1.2.0_amd64.AppImage, .debLinux
my-app-1.2.0.osappAndroid (OpenShell app, Termux), servers, any host
downloads.jsonmachine-readable list: platform, arch, URL, size, SHA-256
index.htmldownload page that offers the visitor's system first

https://github.com/<owner>/<repo>/releases/latest always points at the newest release. Without GitHub, build on each system and run openshell release manifest dist --base-url https://example.com/my-app/v1.2.0 to get the same downloads.json and page for any web server.

Update checks#

"package": { "update_url": "https://github.com/<owner>/<repo>/releases/latest/download/downloads.json" }

openshell update and the control API (GET /v1/update) compare the running version with the newest release and return the right download for the current system. Installing updates automatically (download, verify, replace) is planned.

Signing#

Unsigned installers trigger SmartScreen / Gatekeeper warnings. Configure signing in openshell.json; secrets stay in the environment or the certificate store:

"package": {
  "signing": {
    "windows": { "certificate_thumbprint": "A1B2…", "timestamp_url": "http://timestamp.digicert.com" },
    "macos": { "signing_identity": "Developer ID Application: Example Inc. (TEAMID)" }
  }
}
PlatformSettingNotes
Windowscertificate_thumbprintCertificate in the user's/machine's store (import a .pfx first); SHA-256 digest
Windowssign_commandAny signer, e.g. Azure Trusted Signing or a cloud HSM: ["trusted-signing-cli", "-e", "…", "%1"] (%1 = file)
Windowstimestamp_urlRFC 3161 timestamp server, keeps signatures valid after the certificate expires
macOSsigning_identityDeveloper ID Application: … (hardened runtime on), - for ad-hoc
macOSentitlements, provider_short_nameOptional
macOSnotarisationAPPLE_ID, APPLE_PASSWORD, APPLE_TEAM_ID (or APPLE_API_KEY, APPLE_API_ISSUER) in the environment

The release workflow imports certificates from repository secrets (WINDOWS_CERTIFICATE, APPLE_CERTIFICATE, …, see the comments at its top). Certificates and Apple Developer accounts are not part of OpenShell – you need your own.
