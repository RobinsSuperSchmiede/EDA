Architecture

OpenShell separates the shell (generic, built once) from the application (frontend, backend, data – owned by the developer and changeable at any time by humans or agents). The shell contains no application logic; it reads a configuration and manages external components.

Components#

┌──────────────────────────── openshell-desktop (Tauri 2) ─────────────────────────────┐
│  main window ── WebView ── initialization script (window.__OPENSHELL__ + bridge.js)   │
│  tray menu · notifications · approval dialogs · loading screen · runtime panel       │
│                                   │ implements `Host`                                │
│  ┌────────────────────────────── openshell-core ───────────────────────────────────┐ │
│  │ Shell = Runtime + UiHub + Approvals + AuditLog + Policies + control API          │ │
│  │ control API (127.0.0.1 only): REST /v1/* · MCP /mcp · WebSocket /v1/ui/bridge    │ │
│  │ tool execution (exec.rs) · project-scoped file access (fs.rs)                    │ │
│  └──────────────┬───────────────────────────────────────────┬─────────────────────┘ │
│                 │                                           │                       │
│  ┌──── openshell-runtime ─────┐            ┌──────── openshell-agent ────────────┐  │
│  │ plan: ports, ${vars}, probes│            │ policy · approvals · audit          │  │
│  │ supervisor per service      │            │ UiHub (bridge sessions, actions)    │  │
│  │ health checks · log store   │            │ tool catalogue · MCP JSON-RPC       │  │
│  │ static server + proxy       │            │ provider discovery · bridge.js      │  │
│  │ file watcher · job objects  │            └─────────────────────────────────────┘  │
│  └─────────────────────────────┘                                                     │
│                 openshell-config: schema · parsing · validation · interpolation      │
└──────────────────────────────────────────────────────────────────────────────────────┘
        ▲ HTTP (token)                    ▲ MCP stdio→HTTP                ▲ WebSocket
   openshell CLI                   openshell mcp (agents)           pages running bridge.js

The same openshell-core::Shell runs inside the desktop app and inside the CLI (--headless). All three operating modes therefore share one runtime implementation; they differ only in the Host (desktop window vs. headless) and the permission defaults (development vs. production).

Platform differences sit below the runtime in a RuntimeAdapter (crates/runtime/src/platform.rs): the DesktopAdapter (desktop, server) starts any program, the AndroidAdapter only system tools and programs bundled with the app. Hosts forward app lifecycle events (foreground, background, low_memory, ...). The core and the CLI build for Android; see Platforms.

Key decisions#

DecisionRationale
Tauri 2 + Rust for the shellSmall binaries, system WebView (WebView2/WebKit), cross-platform, strong process control in Rust.
Generic shell binary (openshell-desktop) instead of generating a Tauri project per appNo fork, no per-app Rust code, improvements reach every app. Per-app branding/packaging is a later phase.
Services are external processesAny language; code changes never require rebuilding the shell; crash isolation.
Supervisor task per service with a desired-state channel (watch)Start/stop/restart are just changes of the desired state; the supervisor reconciles. Races (start while stopping) resolve naturally.
Ports allocated up front ("port": "auto"), ${...} variablesAll URLs are known before anything starts, so services can reference each other and the frontend can proxy to the backend.
Control API on 127.0.0.1 with tokensOne interface for CLI, SDK and agents. runtime.json (in .openshell/) tells local tools where the shell runs.
Two tokens: admin (CLI/agents) and app (frontend SDK)The frontend gets only /v1/sdk/* and the bridge, limited by agents.sdk_permissions.
Host + Origin checks, CORS allow-listProtects the loopback API against DNS rebinding and against other websites in the user's browser.
MCP as adapter, own tool API as coreMCP is the primary integration for agents (openshell mcp, POST /mcp), but every tool is also plain HTTP/JSON, so non-MCP agents and scripts work too.
Semantic UI bridge (DOM/accessibility) over pixelsElement refs, roles and names are robust and cheap for models. The bridge is injected into the WebView and the static server, so it works for any framework and in browser mode. Screenshots/vision can be added later as a fallback.
Capabilities from config and from the frontendBackends expose functions declaratively (HTTP/task); frontends register UI-level actions at runtime via the SDK. Agents prefer them over UI automation.
Permission scopes + approval queue + audit logAgents never get blanket OS access. Production defaults to read/ui/actions. Critical scopes require a human decision (dialog or CLI); everything is logged to .openshell/audit.jsonl.
Project-scoped file toolsfs_* tools resolve paths relative to the project root, reject .., absolute paths, symlink escapes and .openshell/.
No arbitrary shell commands for agentsOnly tasks declared in the config (task_run, scope system).
Two agent profiles (/mcp full, /mcp/app app)Agents that use an application should see a small, domain-specific tool list (its capabilities, OpenAPI operations, frontend actions), not 32 developer tools.
OpenAPI importMost backend frameworks already describe their API; importing it makes apps agent-usable without extra code.
Installers re-brand the generic binary (openshell-package)Copy openshell-desktop, replace the exe icon (editpe), put the app into app/, run the Tauri bundler. No per-app compilation, so every app gets shell updates by re-packaging.
Per-user state for installed appsruntime.json, logs, audit and OPENSHELL_DATA_DIR go to the user's local data directory (bundle identifier), never into the install directory.
Title bar menu via window subclassing (Windows)Right-clicking the caption (WM_NCRBUTTONUP/HTCAPTION) opens a Tauri popup menu with live service data instead of the system menu; Alt+Space keeps the system menu. Tray (all platforms) and menu bar (macOS) show the same menu.
Independent building blocks (frontend, backend, database, functions)No part is mandatory. A database is managed by the shell itself (SQLite, migrations, WAL) so a frontend or agent functions can store data without a backend; functions are scripts run per call (JSON over stdin/stdout) so an AI interface needs no server. openshell add edits openshell.json while keeping key order.
Platform adapters instead of platform forksOne core for desktop, server and Android. Only command construction, capabilities and lifecycle differ, so agents, MCP, databases and the control API behave identically everywhere. services[].platforms lets one project describe what runs where.
Remote gateway exposes only the app profileOther devices get the app's functions (MCP) with a separate pairing token – never developer tools or the admin token. Browser requests are rejected; TLS and per-device pairing come with the device mesh.
Build steps run inside the supervisorCompile → start → watch → recompile is one lifecycle; build errors become a failed state with compiler output in the logs, retried on the next change.

Lifecycle of openshell dev#

  1. CLI loads and validates openshell.json, checks that no instance runs, launches openshell-desktop --project … --mode development in its own process group.
  2. Desktop: Shell::launch builds the plan (ports, URLs, probes), binds the control API, writes .openshell/runtime.json, creates the main window with the loading page and the initialization script.
  3. Shell::start sets all autostart services to "run". Supervisors wait for dependencies, run setup steps, spawn processes, pipe logs, probe health.
  4. When the frontend is healthy the main window navigates to its URL; bridge.js connects back over WebSocket.
  5. File changes → backend restart / window reload. Crashes → restart with backoff, failed after N crashes per minute.
  6. The CLI follows logs and approval requests via the control API. Ctrl+C or openshell stop → POST /v1/shutdown → services stop in reverse dependency order → window closes.

Security model (summary)#

  • Threats considered: other websites in the user's browser (CSRF / DNS rebinding against the loopback API), a frontend page trying to escalate, agents acting outside their remit, path traversal.
  • Not a sandbox against local malware: any local process running as the user can read runtime.json. The permission system is a policy layer for cooperating agents, the audit log provides accountability.

See Agent Interaction Layer for details.
