Platforms: desktop, server and Android

OpenShell is not tied to the desktop. The runtime, the agent layer, the control API and the configuration are the same everywhere; a small platform adapter decides how programs are started and how the app lifecycle is handled. This page describes the platform model, what works on Android today and where the Android work is going.

Goals#

  • One core, several platforms. openshell-core runs unchanged on Windows, macOS, Linux, headless servers and Android. Platform code lives in adapters and hosts, not in the core.
  • The phone as a personal runtime and mini server. Apps, services, databases, automations and agents generated by AI run locally on the phone and stay reachable for your other devices.
  • AI builds, the user does not edit code. Agents create, extend, test and manage apps through the same MCP tools as on the desktop; the platform tells them which building blocks exist there.
  • Connected devices. Desktop, phone and server are meant to manage and develop projects together (see device mesh).

Configuration#

{
  "services": [
    { "name": "compiler", "command": "cargo run", "platforms": ["desktop", "server"] },
    { "name": "sync", "command": ["node", "sync.mjs"], "background": "pause" }
  ],
  "runtime": { "remote": { "enabled": true, "bind": "0.0.0.0", "port": 7420 } }
}
  • services[].platforms – only run on these platforms. Like modes, services for other platforms are left out of the plan and dependencies on them are dropped.
  • services[].background – keep (default) or pause: stop while the app is in the background, start again when it returns. Only matters on platforms with background: foreground_service.
  • runtime.remote – the remote gateway.

Android#

What runs on Android#

Android allows an app to execute only files inside its APK (the native library directory) and system tools – files written at runtime cannot be executed (W^X, Android 10+). There is no PATH with toolchains. The AndroidAdapter follows these rules and turns violations into a clear error that tells the developer or the agent what to use instead:

`cargo` cannot run on Android: apps may only start system tools and programs shipped with the
app (bundled: node). Use a static frontend, the built-in database or functions for a bundled
interpreter, or limit this service with "platforms": ["desktop", "server"]
Building blockOn Android
Static frontend (frontend.dist)✅ built-in static server
Built-in database (SQLite, migrations, SDK, agents)✅ compiled into OpenShell
Functions (capabilities[].run)✅ with system tools (sh) or a bundled interpreter
Services✅ with a bundled program (node, python, own binaries in the APK)
HTTP capabilities, OpenAPI import, UI bridge, MCP✅ unchanged
Dev-server frontends, build steps with toolchains❌ – build on the desktop, or limit with platforms

The host registers what it bundles:

let adapter = AndroidAdapter::new()                        // allows /system/bin
    .with_executable_dir(native_library_dir)               // every executable in the APK
    .with_program("node", native_library_dir.join("libnode.so"))
    .with_program("python", native_library_dir.join("libpython.so"));
let shell = Shell::launch_with(project, Mode::Production, host, Arc::new(adapter)).await?;

Without a host the adapter reads OPENSHELL_ANDROID_EXEC_DIRS (:-separated) and OPENSHELL_ANDROID_PROGRAMS (node=/path/libnode.so;python=/path/libpython.so). Inside Termux the TermuxAdapter is used instead.

Termux: apps on the phone#

Termux is a Linux environment for Android with its own package manager. The OpenShell CLI runs there and detects it ($PREFIX / $TERMUX_VERSION), so the phone becomes a development machine and a portable host – no computer needed:

curl -fsSL https://raw.githubusercontent.com/RobinsSuperSchmiede/EDA/main/scripts/install.sh | sh
pkg install python nodejs openjdk-17 rust golang postgresql   # what your apps need
openshell create notes --with frontend,backend,database
cd notes && openshell dev          # dev server, file watching, agents – like on the desktop
openshell start --headless         # production; open the URL in the phone's browser
openshell package --target bundle  # notes-0.1.0.osapp for the Android app or other hosts
  • Every program from $PREFIX/bin runs: services, setup and build steps (npm install, pip, cargo build, mvn), dev servers and functions. python falls back to python3.
  • openshell doctor shows the platform and turns missing programs into pkg install … hints.
  • While an app runs, OpenShell holds a Termux wake lock (termux-wake-lock, from the Termux:API package) so services keep running with the screen off, and releases it on stop.
  • Databases: the built-in SQLite needs nothing; PostgreSQL, Redis or MariaDB from pkg run as services and can be exposed to other devices.
  • OPENSHELL_ANDROID_MODE=app forces the restricted app adapter (to test what the Android app allows); OPENSHELL_ANDROID_MODE=termux forces the Termux adapter in Termux-like environments.

Lifecycle, battery and network#

Android stops apps in the background. The host forwards the Activity and system events:

AndroidLifecycleEventEffect
onStartforegroundpaused services start again
onStopbackgroundservices with "background": "pause" stop
onTrimMemory(RUNNING_CRITICAL)low_memorypausable services stop
PowerManager.isPowerSaveModepower_savereported to agents and hosts
ConnectivityManager callbacknetworkreported (connected, metered)

Runtime::keep_alive() lists the active services that must keep running (background: keep). While it is not empty the Android host keeps a foreground service (type specialUse or dataSync, with a persistent notification) alive and asks the user once to exempt the app from battery optimisation, so the phone can act as an always-on server. When the list becomes empty the host stops the foreground service and Android may suspend the app.

Hosts send events with Shell::lifecycle(event); for testing on any platform use the CLI or API:

openshell lifecycle background     # services with "background": "pause" stop
openshell lifecycle foreground     # … and start again
curl -X POST -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" -d '{"kind":"low_memory"}' $URL/v1/lifecycle

Status#

  • ✅ The core and the CLI build for aarch64-linux-android and x86_64-linux-android (CI checks the Android build on every push).
  • ✅ Verified on an Android 16 emulator: openshell dev --headless serves a static frontend, migrates the database, runs functions through /system/bin/sh, leaves desktop-only services out, pauses and resumes services on lifecycle events and serves the app profile to a laptop through the remote gateway.
  • ✅ Termux: TermuxAdapter with toolchains, wake lock and pkg install hints; prebuilt CLI for aarch64-linux-android in releases, install.sh detects Termux.
  • 🚧 Android app: Kotlin host + JNI bridge in apps/android / crates/android, AAB build for the Play Store in CI – see Android app.

The Android app#

The OpenShell Android app is a host around the unchanged core – see Android app:

  1. Shell app – Kotlin Activity with a WebView (no JavaScript bridge for app pages) and the core as a JNI library (libopenshell_android.so).
  2. Foreground service (specialUse) – keeps the runtime alive, shows a notification with the running services, forwards lifecycle, memory and network events, partial wake lock.
  3. App manager – install apps from .osapp bundles (file picker, share sheet), open, stop.
  4. Bundled runtimes (planned) – Node.js and Python as lib*.so in the APK, registered automatically when present.
  5. On-device agents – remote agents through the gateway today; local models planned.

Remote access#

The remote gateway makes an app usable from other devices – a laptop agent using functions of an app hosted on the phone, a browser opening a website the phone serves, a desktop tool using a database on the phone. Off by default; tokens per device, an address allowlist, rate limits with lockout, TLS, opt-in exposure per service and an audit trail can be combined:

"runtime": { "remote": { "enabled": true, "allow": ["192.168.1.0/24"], "tls": { "enabled": true },
                         "expose": [{ "service": "frontend", "port": 8080 }] } }
openshell remote pair laptop     # token for one device, QR code, links
openshell remote                 # URLs, fingerprint, devices, blocked addresses

Full guide: Remote access.

Device mesh (in progress)#

Desktop, phone and server running OpenShell should form one personal mesh:

  • ✅ Pairing – per-device tokens with a QR code / pairing URI (openshell remote pair), TLS with pinned self-signed certificates, revocation per device.
  • Discovery – mDNS (_openshell._tcp) in the local network, VPN addresses otherwise.
  • Remote control API – manage services, logs and approvals of another device's apps with the same CLI (openshell --device phone status).
  • Project sync – projects as folders synchronised between devices (git-based), so an agent can develop on the desktop and deploy to the phone (openshell deploy --device phone).
  • Placement – services[].platforms already lets one project describe what runs where; the mesh adds "run this service on the server, the UI on the phone".
