Agent Interaction Layer

OpenShell gives AI agents a standardized, model-agnostic interface to a running desktop application – in two profiles:

ProfileForTools
app ("use the app")assistants that should work with the application, e.g. Claude Desktop on the user's PConly the application's own functions (list_todos, add_todo, …) + app_status
full ("develop the app")coding agents that build and evolve the applicationeverything below: runtime, logs, services, files, UI automation, capabilities

Neither profile needs the UI: the app profile calls the application's API directly; UI automation is an extra for the full profile.

In the full profile agents can

  • query application and runtime state, read logs,
  • start, stop and restart services,
  • see and operate the user interface (semantic snapshot, click, fill, navigate, …),
  • discover and invoke application capabilities,
  • read and modify project files (scoped to the project),
  • run declared tasks,

all subject to permission scopes, optional human approval and an audit log. OpenShell does not ship or prescribe an AI model – it is infrastructure for any agent: Claude Code, Codex, Cursor, OpenAI- or Anthropic-based agents, local models via Ollama / LM Studio, or your own agent system.

The agent layer is opt-in. An app opens it with "agents": { "enabled": true } – openshell create, openshell init and openshell add function write that for you, openshell agents enable / disable switch it. While it is off, the MCP endpoints, the tools API, the UI bridge and the remote gateway's MCP endpoint refuse every request and no bridge script is injected into the app's pages; the app, its frontend SDK and exposed services keep working. openshell agents shows what agents get right now.

Connecting#

Using an installed app#

Installed apps (see Installers and releases) are MCP servers themselves:

{ "mcpServers": { "my-app": { "command": "C:\\Users\\me\\AppData\\Local\\Programs\\My App\\my-app.exe", "args": ["--mcp"] } } }

If the app is not running, it starts in the background without a window, so an agent can use it while the user does something else. Opening the app later replaces the background instance with the window. The tool list contains only the app's functions; permissions follow agents.permissions.production. Add --profile full for the developer tool set. The runtime panel (title bar right-click → Runtime panel) shows both commands ready to copy.

Using a project from the CLI#

openshell mcp --app --start --project /path/to/app   # app profile, start headless (production) if needed

Developing: MCP over stdio (recommended)#

openshell mcp --project /path/to/app            # add --start to launch `openshell dev --headless` on demand

Configure it as an MCP server in your client:

claude mcp add my-app -- openshell mcp --project /path/to/app       # Claude Code
{ "mcpServers": { "my-app": { "command": "openshell", "args": ["mcp", "--project", "/path/to/app"] } } }

The stdio server forwards to the running shell and reconnects automatically, so the agent can be started before the app. If the app is not running, tools/list still works and tool calls explain how to start it.

MCP over HTTP#

POST {control_url}/mcp (full profile) and POST {control_url}/mcp/app (app profile) implement the Streamable HTTP transport (JSON responses). They require Authorization: Bearer <token> from .openshell/runtime.json. Because the port and token change on each start, stdio is more convenient; set runtime.control_port for a fixed port.

From another device (remote gateway)#

With "runtime": { "remote": { "enabled": true } } the app profile is also reachable from other devices – for example an agent on a laptop using an app hosted on a phone. openshell remote prints the URL and a ready MCP client configuration ({ "url": "http://<ip>:7420/mcp/app", "headers": { "Authorization": "Bearer <pairing token>" } }). Only the app's functions are exposed; see Platforms.

Plain HTTP / JSON#

GET  /v1/tools                      list tools with permission and access (allowed / approval / denied)
POST /v1/tools/{name}               body = arguments → { "ok": true, "result": ... } or { "ok": false, "result": { "error": "..." } }

Send X-OpenShell-Agent: <name> to identify the agent in the audit log. From a terminal: openshell call <tool> '<json>'.

Resources and notifications#

Besides tools, the MCP server offers read-only resources: openshell://status, openshell://config, openshell://logs, openshell://capabilities (developer profile), openshell://app (app profile) and openshell://db/<name>/schema for every database agents may read.

openshell mcp (stdio) sends notifications/tools/list_changed whenever the tool list changes – for example when the frontend registers an action, an OpenAPI document is imported or the app is started after the agent connected.

UI automation#

ui_snapshot returns a compact, semantic view of the page:

{
  "url": "http://127.0.0.1:52471/",
  "title": "Todo App",
  "headings": [{ "level": 1, "text": "Todo App" }],
  "elements": [
    { "ref": "e1", "role": "textbox", "name": "New todo", "value": "" },
    { "ref": "e2", "role": "button", "name": "Add" },
    { "ref": "e6", "role": "checkbox", "name": "Buy milk", "checked": false }
  ],
  "text": "Todo App 3 todos · 1 done …",
  "actions": [{ "name": "set_filter", "description": "…" }]
}

Use the refs with ui_click {"ref": "e2"} or ui_fill {"ref": "e1", "value": "…", "submit": true}. Refs stay stable while the element exists; take a new snapshot after larger UI changes. The bridge (bridge.js) is injected into the desktop WebView and into pages served by OpenShell's static server, so it works with any framework and also in browser mode (openshell dev --headless). Password values are never included in snapshots.

Capabilities: the application's own functions#

Prefer capabilities over UI automation – they are faster and more reliable, and they are what the app profile exposes. Three sources:

  • OpenAPI import – set "openapi": "/openapi.json" (FastAPI), "/v3/api-docs" (Spring/springdoc), "/swagger/v1/swagger.json" (ASP.NET) or a file/URL on a service. When the service becomes healthy, every operation becomes a tool: name from operationId, input schema from path/query parameters and the JSON request body, GET → scope read, other methods → actions. Filter with { "location": "...", "include": [...], "exclude": [...], "prefix": "shop" }.
  • Declared in openshell.json (capabilities), backed by an HTTP endpoint, a script (run – JSON in on stdin, JSON out on stdout, no server needed) or a task.
  • Databases: with agent_access read/write, the app profile also offers db_list, db_schema, db_query and db_execute – an app can be only a database plus functions.
  • Registered by the frontend at runtime with the SDK:
OpenShell.agent.registerAction("set_filter", {
  description: "Show all, open or done todos",
  permission: "ui",
  input_schema: { type: "object", properties: { filter: { enum: ["all", "open", "done"] } } },
}, ({ filter }) => setFilter(filter));

Permissions and approvals#

Every tool needs exactly one scope:

ScopeAllowsDefault devDefault prod
readstate, logs, config, capabilities list✅✅
uiUI automation, window control, notifications✅✅
actionscapabilities that change data✅✅
servicesstart/stop/restart services✅–
filesread project files✅–
codewrite project files✅–
systemdeclared tasks, JavaScript evaluation––

Configure with agents.permissions. Scopes in agents.approval_required (default ["system"]) need a human decision: the desktop app shows a dialog (and the runtime panel lists pending requests), headless mode prints the request; answer with openshell approve <id> / openshell deny <id>. Unanswered requests are denied after approval_timeout_ms.

Every call – allowed, denied, rejected or failed – is appended to .openshell/audit.jsonl with agent name, channel, tool, scope, (truncated) arguments, outcome and duration. View it with openshell audit.

The runtime panel of the desktop app (title bar right-click → Runtime panel → AI agents) shows the effective permissions: what each scope allows, development vs. production, which scopes ask for approval, and every agent session and paired device with what it effectively may do. The same data: openshell agents, GET /v1/agents.

Agent sessions#

By default every agent connected through openshell mcp uses the admin token of .openshell/runtime.json and gets the app's agent permissions. To tell agents apart and limit each one, give it its own session:

openshell agents token claude --scopes read,actions       # app profile: only the app's functions
openshell agents token builder --full                      # developer tools as well
openshell agents tokens                                    # list
openshell agents revoke claude                             # stops working at once, also while the app runs

The token (osa_…) is shown once and stored as a SHA-256 hash in <data>/agent-sessions.json. Use it with openshell mcp --token osa_…, the environment variable OPENSHELL_AGENT_TOKEN (also for an installed app's --mcp), or as Authorization: Bearer on the control API. A session

  • gets at most what agents.permissions grants in the current mode, limited to its --scopes,
  • with the app profile may only use /mcp/app; with --full also /mcp and /v1/tools – never the admin API,
  • is written to the audit log as session:<name>.

openshell agents token prints a ready MCP client configuration:

{ "mcpServers": { "claude": { "command": "openshell", "args": ["mcp", "--app", "--project", "/path/to/app"],
  "env": { "OPENSHELL_AGENT_TOKEN": "osa_…" } } } }

Paired devices on the remote gateway work the same way: openshell remote pair laptop --scopes read limits what an agent on that device may do.

Security#

  • The control API listens on 127.0.0.1 only and requires a bearer token. The admin token lives in .openshell/runtime.json (mode 0600 on Unix, ignored by git).
  • Requests with a foreign Host header (DNS rebinding) or a non-allow-listed Origin (other websites) are rejected.
  • The frontend gets a separate app token limited to /v1/sdk/* and the bridge, with agents.sdk_permissions.
  • Application frontends loaded from http(s) URLs get no Tauri IPC access.
  • File tools reject absolute paths, .., symlink escapes and OpenShell's state directory; fs_write also protects .git.
  • Agents cannot run arbitrary shell commands; only tasks declared in the config, under the system scope.
  • The remote gateway (off by default) exposes only the app profile, uses its own pairing token, rejects browser requests (Origin) and audits calls with the channel remote. Device tokens can carry their own scopes.
  • Agent session tokens (osa_…) reach only the MCP endpoints and the tools API, never the admin API.
  • With agents.enabled: false (the default) agents cannot connect at all.
  • Limits: the permission layer governs cooperating agents. A local process running as the same user can read the token file; OpenShell is not a sandbox against local malware.

A typical agent loop#

  1. app_info → understand the app, its services and capabilities.
  2. Edit code with the agent's own file tools (or fs_write).
  3. Services with watch restart automatically; otherwise service_restart. Check runtime_status / logs_read {"errors_only": true}.
  4. ui_reload (static frontends reload automatically), then ui_snapshot and ui_click / ui_fill to verify the feature like a user would.
