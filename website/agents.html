Give agents the app
Not your screen

OpenShell turns an application into a set of tools over MCP and plain HTTP. Assistants use the app's own functions. Coding agents get what they need to build, run and verify it. Every call is checked against a scope and written to an audit log.

Two profiles

Use it or build it
One protocol

app profile

Use the app

For assistants that should work with the application, for example on a user's PC. The tool list holds only the app's own functions plus app_status: declared capabilities, imported OpenAPI operations, frontend actions and databases as far as you allow. No UI needed.

# a project openshell mcp --app --start --project /path/to/app # an installed app my-app.exe --mcp
developer profile

Build the app

For coding agents that evolve the application. All 32 tools: state, logs, services, files, databases, semantic UI automation, declared tasks, capabilities. Production apps reduce what is allowed.

openshell mcp --project /path/to/app › app_info services, capabilities, hints › logs_read 0 errors
Connect

Add it to your client

The stdio server forwards to the running shell and reconnects by itself, so the agent can start before the app does. With --start it launches the app when needed.

claude mcp add my-app     -- openshell mcp --app --start --project /path/to/my-app   # use
claude mcp add my-app-dev -- openshell mcp --project /path/to/my-app                 # develop

Claude Desktop, Cursor and other clients that read an mcpServers block:

{
  "mcpServers": {
    "my-app": {
      "command": "openshell",
      "args": ["mcp", "--app", "--start", "--project", "/path/to/my-app"]
    }
  }
}

Installed apps are MCP servers themselves. If the app is not running it starts in the background without a window, and opening it later replaces that instance with the window. Add --profile full for the developer tools.

{
  "mcpServers": {
    "my-app": {
      "command": "C:\\Users\\me\\AppData\\Local\\Programs\\My App\\my-app.exe",
      "args": ["--mcp"]
    }
  }
}

Streamable HTTP at POST {control_url}/mcp (developer) and /mcp/app (app) with Authorization: Bearer <token> from .openshell/runtime.json. The port and token change on every start; set runtime.control_port for a fixed port. For scripts, plain JSON:

GET  /v1/tools                  # tools with scope and access: allowed, approval, denied
POST /v1/tools/{name}           # body = arguments, header X-OpenShell-Agent: my-agent
openshell call ui_click '{"text":"Save"}'

An agent on a laptop can use an app hosted on a phone or server. The gateway offers the app profile only, never developer tools. Pair the laptop, then give the client this block:

{
  "url": "https://192.168.1.20:7420/mcp/app",
  "headers": { "Authorization": "Bearer osd_…" }
}

Create the token with openshell remote pair laptop. See remote access.

Besides tools, the MCP server offers read-only resources (openshell://status, config, logs, capabilities, database schemas) and sends tools/list_changed when the tool list changes. Defaults can be changed with agents.permissions.

Capabilities

The app's own functions
Better than clicking

Prefer capabilities over UI automation: they are faster and more reliable, and they are all the app profile exposes. An app offers them in four ways.

openapi

Import

Point at /openapi.json (FastAPI), /v3/api-docs (Spring) or an ASP.NET document. Every operation becomes a tool; GET is read, the rest is actions.

declared

In the config

Back a capability with an HTTP endpoint, a script (JSON in, JSON out, no server) or a task.

database

Built-in SQLite

With agent_access set to read or write, agents get db_query and db_execute for that database.

frontend

Registered live

The UI registers actions with the SDK while it runs, for things only the page can do.

UI automation

Elements, not pixels

When there is no function for it, ui_snapshot gives the agent a compact, semantic view of the page: headings, dialogs, text and interactive elements with stable references. It works with any framework, in the desktop window and in browser mode.

Use the refs with ui_click {"ref": "e2"} or ui_fill {"ref": "e1", "value": "…", "submit": true}. Password values are never included. A screenshot fallback for canvas-heavy UIs is planned.

{
  "url": "http://127.0.0.1:52471/",
  "title": "Todo App",
  "headings": [{ "level": 1, "text": "Todo App" }],
  "elements": [
    { "ref": "e1", "role": "textbox", "name": "New todo", "value": "" },
    { "ref": "e2", "role": "button", "name": "Add" },
    { "ref": "e6", "role": "checkbox", "name": "Buy milk", "checked": false }
  ]
}
Control

Allowed, asked,
or denied

  • Scopes per mode. Development is broad, production narrow. openshell tools shows what each tool needs and what is currently allowed.
  • Approvals. Scopes in approval_required (default system) wait for a person. The desktop app shows a dialog; headless mode prints a request. Unanswered requests are denied.
  • Audit. Every call, allowed or not, is appended to .openshell/audit.jsonl with the agent's name, channel, tool, scope and outcome.
  • Fenced files. Absolute paths, .. and symlink escapes are rejected. There is no way to run arbitrary shell commands.
  • Limits. The permission layer governs cooperating agents. It is not a sandbox against local malware.
$ openshell tools # every tool with its scope and current access $ openshell approvals # requests waiting for a person $ openshell approve <id> # or: openshell deny <id> $ openshell audit -n 30 # the last 30 agent actions $ openshell call ui_snapshot # try any tool from the terminal
The loop

How a coding agent
works on an app

01 · look

app_info

Understand the app, its services and capabilities before touching anything.

02 · change

Edit code

With the agent's own file tools or fs_write.

03 · check

Status and logs

Services with watch restart by themselves. Read runtime_status and errors in logs_read.

04 · verify

Use it like a person

ui_reload, then ui_snapshot, ui_click and ui_fill on the new feature.
